## Overview

This API provides comprehensive backend services for the Drug Plant Management System with GAP (Good Agricultural Practices) compliance tracking. The system supports three user roles with different permission levels:

- **USER**: Regular farmers who manage their own plots
- **ADMIN**: Regional administrators who oversee specific geographical areas (province/district/subdistrict)
- **SUPER_ADMIN**: System administrators with full access

### Key Features

- JWT-based authentication with PIN verification for admin roles
- Location-based access control (Admin can only access users/plots in their assigned region)
- Complete GAP compliance tracking (Categories 1.1-1.7)
- Traceability system with QR code support
- File upload for images and documents
- Real-time notifications

---

## Authentication

The API uses JWT (JSON Web Token) for authentication. Admin and Super Admin roles require additional PIN verification.

### Authentication Flow

#### For Regular Users (USER role):
1. **Signup** → Receive access token + refresh token
2. **Signin** → Receive access token + refresh token
3. Use access token in `Authorization: Bearer <token>` header

#### For Admin/Super Admin roles:
1. **Signin** → Receive `tempToken` + `requiresPin: true`
2. **Verify PIN** → Receive access token + refresh token
3. Use access token in subsequent requests

### Token Refresh
- Access tokens expire after a set duration
- Use refresh token to obtain new access token without re-authentication

## Core Concepts

### Role-Based Access Control

| Role | Permissions |
|------|------------|
| **USER** | - Manage own profile<br/>- Create/edit/delete own plots<br/>- Manage GAP records for own plots |
| **ADMIN** | - View/manage users in assigned region<br/>- View/approve plots in assigned region<br/>- Generate reports for assigned region |
| **SUPER_ADMIN** | - Full system access<br/>- Create/manage admin accounts<br/>- View all users and plots |

### Admin Scoped Permission

Admins can only access data within their assigned geographical scope:
- **Province Level**: Access all districts and subdistricts in the province
- **District Level**: Access all subdistricts in the district
- **Subdistrict Level**: Access only that specific subdistrict

### Soft Delete

Most resources use soft delete (set `deletedAt` timestamp) rather than permanent deletion, allowing data recovery.

## 1. Authentication Endpoints

### POST /api/v1/auth/signup
Register a new user account.

**Authentication:** None (Public)

**Request Body:**
```json
{
  "phone": "0812345678",
  "birthday": "1990-01-15",
  "firstName": "สมชาย",
  "lastName": "ใจดี",
  "idCard": "1234567890123",
  "province": "เชียงใหม่",
  "district": "เมืองเชียงใหม่",
  "subDistrict": "ศรีภูมิ",
  "address": "123 หมู่ 5",
  "postalCode": "50200"
}
```

**Success Response (201):**
```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refreshToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user": {
    "id": "clxxx123",
    "phone": "0812345678",
    "firstName": "สมชาย",
    "lastName": "ใจดี",
    "role": "USER"
  }
}
```

**Error Responses:**
- `400`: Invalid input data
- `409`: Phone number already exists
- `429`: Too many signup attempts

## Error Handling

All endpoints follow consistent error response format:

### Error Response Format

```json
{
  "statusCode": 400,
  "message": "Validation failed",
  "error": "Bad Request",
  "details": [
    {
      "field": "phone",
      "message": "phone must be a valid phone number"
    }
  ]
}
```

### Common HTTP Status Codes

| Code | Meaning | Description |
|------|---------|-------------|
| 200 | OK | Request successful |
| 201 | Created | Resource created successfully |
| 400 | Bad Request | Invalid input data |
| 401 | Unauthorized | Missing or invalid authentication token |
| 403 | Forbidden | Insufficient permissions |
| 404 | Not Found | Resource not found |
| 409 | Conflict | Resource already exists (e.g., duplicate phone) |
| 413 | Payload Too Large | File size exceeds limit |
| 422 | Unprocessable Entity | Validation error |
| 429 | Too Many Requests | Rate limit exceeded |
| 500 | Internal Server Error | Server error |

### 2. Admin PIN Flow

```javascript
// Step 1: Signin
const signinResponse = await api.post('/auth/signin', { phone, birthday });

if (signinResponse.requiresPin) {
  // Step 2: Show PIN input modal
  const pin = await showPinModal();
  
  // Step 3: Verify PIN
  const verifyResponse = await api.post('/auth/verify-pin', {
    tempToken: signinResponse.tempToken,
    pin: pin

}
```

### 6. Error Handling Best Practices

```javascript
try {
  const response = await api.post('/plots', plotData);
} catch (error) {
  if (error.response) {
    // Server responded with error
    switch (error.response.status) {
      case 400:
        showValidationErrors(error.response.data.details);
        break;
      case 401:
        redirectToLogin();
        break;
      case 403:
        showMessage('คุณไม่มีสิทธิ์เข้าถึงข้อมูลนี้');
        break;
      case 404:
        showMessage('ไม่พบข้อมูลที่ต้องการ');
        break;
      default:
        showMessage('เกิดข้อผิดพลาด กรุณาลองใหม่อีกครั้ง');
    }
  } else if (error.request) {
    // No response from server
    showMessage('ไม่สามารถเชื่อมต่อกับเซิร์ฟเวอร์ได้');
  }
}
```
